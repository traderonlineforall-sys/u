# ترقية هوية الجهاز الموثوقة

هذه النسخة تحافظ على نفس اسم المستخدم وكلمة السر المشتركة للتول، ولا تحتاج إنشاء حساب منفصل لكل مستخدم.

## ما الذي تغير؟

- كل متصفح يولد مفتاحًا عشوائيًا قويًا خاصًا بالجهاز.
- السيرفر يربط المفتاح بكنية واحدة ومعرّف مستخدم واحد.
- الهوية تحفظ في Cookie آمنة `HttpOnly` وموقعة من السيرفر.
- إذا حُذفت الـCookie وبقي مفتاح المتصفح، تستعيد التول نفس الكنية بالمفتاح الدقيق.
- لا يُستخدم IP أو نوع المتصفح أو Canvas لاختيار كنية مستخدم آخر.
- كل الرسائل والاقتراحات والتفاعلات والحذف تستخدم `uid` الموجود داخل الجلسة الموقعة فقط.
- رسائل الـDM لا تُعاد إلا إذا كان المستخدم الحالي طرفًا في الغرفة.

## التثبيت بالترتيب

1. ارفع ملفات هذه النسخة إلى GitHub ثم انتظر نجاح Cloudflare Deploy.
2. افتح Supabase SQL Editor.
3. نفّذ الملف `SUPABASE_TRUSTED_DEVICE_IDENTITY_UPGRADE.sql` مرة واحدة.
4. تأكد أن متغيرات Cloudflare التالية موجودة:
   - `SESSION_SECRET`
   - `SUPABASE_URL`
   - `SUPABASE_SERVICE_ROLE_KEY`
   - `BASIC_AUTH_USER`
   - `BASIC_AUTH_PASS`
5. اختياري لكن موصى به: أضف `DEVICE_IDENTITY_SECRET` بقيمة عشوائية قوية مختلفة عن باقي الأسرار. لا تغيّرها بعد تسجيل الأجهزة حتى لا تُلغى هوياتها الموثوقة.

## انتقال المستخدمين الحاليين

المستخدم الذي ما زالت جلسته مفتوحة سيتم ربط جهازه تلقائيًا عند فتح التول. وعند تسجيل الدخول، تقبل الترقية تطابق الجهاز القديم الدقيق فقط ثم تنقله للنظام الجديد. لا توجد استعادة تقريبية أو اختيار كنية بناءً على تشابه IP.

إذا حذف المستخدم جميع بيانات الموقع قبل ربط جهازه، لن تخمّن التول هويته. سيحتاج كنية جديدة أو Reset للكنية القديمة بواسطة الأدمن. هذا مقصود لمنع ربطه خطأ بمستخدم آخر.

## اختبار سريع

1. سجل الدخول من جهاز مستخدم حالي وافتح الصفحة لمدة ثانيتين.
2. سجل الخروج ثم ادخل مجددًا؛ يجب أن تظهر نفس الكنية تلقائيًا.
3. غيّر قيمة `user_id` من أدوات المطور أو داخل طلب API؛ يجب أن يتجاهلها السيرفر ويستخدم هوية الجلسة.
4. حاول فتح DM لا يحتوي معرّف المستخدم الحالي؛ يجب أن يرجع `403`.
5. من Supabase API باستخدام anon key، يجب ألا يمكن قراءة جدول `support_messages` أو `support_device_identities`.
